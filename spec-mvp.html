Community Legibility Spec MVP

The first piece of the Community Legibility Spec to build. Two people see what each other changed, through a shared server, without sending files.

Overview

Status
Designed, not built

What done looks like

One tagged file, through all five parts.

  1. 1

    Manifest mapping

    Your scanner writes each tagged file down as a number and a date. The file stays home.

    See spec
  2. 2

    Cuts and publishing

    To share the work itself, cut a page for someone. A separate act from the manifest.

    See spec
  3. 3

    Visibility system

    One visibility list per file decides which manifest and which cut it lands in.

    No spec yet
  4. 4

    Community Data Commons MCP

    An always-on server answers a member’s AI with only the ids and dates they may see.

    Scroll to section
  5. 5

    Activity log data

    Your record and the community’s overlap. The overlap proves you took part.

    See spec
Prompt for your agent
I'm building the Community Legibility Spec MVP. Write me an end-to-end acceptance test for it.

The test:
1. A file in the Community Owner's vault gets member-b added to the visibility list in its frontmatter.
2. Their scanner writes member-b-manifest.json and syncs it to the community server.
3. The Member's AI calls list_changes over MCP, sending the community token and the identity member-b.
4. The answer contains that file's file_number and last_updated, and no names, paths or content.

Give me the steps as a script I can run, and tell me what each step prints when it passes.

The parts

Six parts. Each one runs in one place.

Scanner · each member’s machine
Walks the vault, reads frontmatter, keeps the files tagged for the community, and writes the redacted manifest and the full manifest. The only part that touches real files.
Community server · always on
Holds each member’s redacted and full manifest, plus the two cuts folders. Needs a long-running Node.js or Python 3 process and a path for manifests to land.
MCP server · on the community server
Reads the manifest on each request and answers. Never reads a member’s vault. Runs as a service that survives reboots.
Cuts folders · on the community server
One drop folder each way: the Community Owner’s cuts for the Member, the Member’s cuts for the Community Owner. A cut is how readable work travels; see Cuts and lenses.
Tailscale node share · between networks
Shares the server with the Member as a single node. They reach the MCP endpoint and nothing else on the machine or the network.
AI client · each member’s machine
claude_desktop_config.json points at the server’s MCP endpoint and carries the community token and the identity.

Who does what

Three roles. The host runs the box; the two members use it.

Host · runs the server
Everything in the host checklist below: the runtime, the MCP server, the service, the sync target and the share.
Community Owner · shares
Tags files, runs the scanner, and syncs their manifest to the server.
Member · connects
Accepts the share, adds the endpoint to their AI client and runs the first query. Later, runs their own half.

Host checklist

Do these in order. Each step ends in a check. Angle brackets mark values you choose.

1 · Runtime and folder
Confirm the server can run a long-lived Node.js or Python 3 process. Make one folder for manifests to land in. Check: one of these prints a version.
node --version
python3 --version
2 · The MCP server
Write a server that exposes the three tools under The MCP tools and reads the manifest file fresh on every call. Serve it over Streamable HTTP so other machines can reach it. Reject any call that is missing the token or the identity. Check: the MCP Inspector connects and lists three tools.
npx @modelcontextprotocol/inspector --server-url http://<server>:<port>/mcp --transport http
3 · Run it as a service
It has to survive reboots. On Linux that is a systemd unit. Check: after a reboot, the status shows it active.
[Unit]
Description=Community MCP server
After=network-online.target

[Service]
ExecStart=<command that starts the server>
User=<service user>
Restart=always

[Install]
WantedBy=multi-user.target
4 · Sync target
Give the Community Owner a way to push their manifest in. The v1 default is rsync over ssh: add their ssh key for a user that can write only to the manifest folder. Check: after they save a tagged file, the manifest’s emitted_at changes.
rsync -av member-b-manifest.json <user>@<server>:<manifest folder>/
5 · Share to the Member
In the Tailscale admin console, open Machines, pick the server, choose Share and invite the Member. A shared machine is quarantined: it takes incoming connections and cannot start them. Limit shared users to the MCP port in the policy file. Check: from the Member’s machine, the MCP port answers and nothing else does.
"grants": [
  {
    "src": ["autogroup:shared"],
    "dst": ["*"],
    "ip": ["<port>"]
  }
]
6 · First query
The Member adds the endpoint (see Client setup) and asks what the Community Owner changed. Check: the answer lists ids and dates, and nothing else.

Build order

Four phases. Each one is a working system on its own.

Phase 1 · Local
Scanner and MCP server on the Community Owner’s machine, over stdio. Done when they query it from their own AI as if they were the Member.
Phase 2 · On the server
Host checklist steps 1 to 4. Done when the Community Owner queries the server over their own network.
Phase 3 · Shared
Host checklist steps 5 and 6. Done when the Member gets the Community Owner’s ids and dates back.
Phase 4 · The Member’s half
The Member runs a scanner on their own vault and shares their node back. Two manifests, two tailnets, never merged. The cross-reference is the dual ledger. find_overlap lands here.

The manifest file

One JSON file per visibility tag. Format v0.1.

File name
member-b-manifest.json for the member-b tag. The server reads it from the folder the host made in step 1.
version
Format version, starting at "0.1".
emitted_at
When the scanner wrote the file, as an ISO 8601 timestamp.
source
Whose vault it describes, for example "megan".
filter
The visibility tag used to select files, for example "member-b". The same scanner writes one file per tag.
files[].file_number
SHA-256 of the file’s vault-relative path, first 6 hex characters, prefixed 0x. v1 computes it every run and writes nothing back. A rename makes a new number; v2 stores a fingerprint-id in frontmatter once.
files[].last_updated
The frontmatter last-updated field, or the file’s modified time when that is missing.
files[].design_principles
The design-principles frontmatter field, joined with any of the five design principles found in tags.
What the Member reads by default
The redacted manifest: file_number and last_updated. Anything deeper is granted per relationship.
Prompt for your agent
Write a manifest scanner for the Community Legibility Spec MVP in <language>.

It walks a folder of markdown files, parses the YAML frontmatter, and keeps files whose visibility list contains the tag I pass, for example member-b. It writes <tag>-manifest.json with:
- version: "0.1"
- emitted_at: when it ran, ISO 8601
- source: whose vault, for example "megan"
- filter: the tag
- files: one entry per kept file, with
  - file_number: SHA-256 of the vault-relative path, first 6 hex characters, prefixed 0x
  - last_updated: the frontmatter last-updated field, else the file's modified time, ISO 8601
  - design_principles: the design-principles field, joined with any principle slugs found in tags (I'll give you the list)

It never writes back to the files. Include a test with three sample files.

The MCP tools

Three tools. Each one checks the token and the identity first, answers only from the manifest file and never opens a vault.

list_changes
What changed since a date. Input: since (string, ISO 8601). Returns: file_number, last_updated and design_principles for each file whose last_updated is after since.
list_principles
The shape of the work without naming any of it. Input: none. Returns: each principle in the manifest, with its file count.
get_principle_activity
One principle over time. Inputs: principle (string) and window (optional, 30 days by default). Returns: last_updated and file_number for each file with that principle, sorted.
find_overlap
Later, in phase 4. Compares two members’ manifests once the Member’s exists.

Every request

Two checks at the door. Both ride on every call, so there is no session to keep.

Community token
Says the caller is in the community. Set in the AI client config.
Identity
Says which member: “I’m member-b”. The server serves only that member’s slice.
Why both
A shared token alone would show everyone everything. The identity does the scoping. Tailscale is the network gate; token and identity are the content gate.
How they travel
Proposed: two HTTP headers on every call, X-Community-Token and X-Member. The names are a suggestion until the host picks them.
Prompt for your agent
Add request checks to my Community Legibility Spec MVP server.

Every call carries two headers: X-Community-Token (shared by members) and X-Member (which member). Reject a call that is missing either one, or whose token does not match. Use the member to choose which slice to serve. There are no sessions: each call stands on its own. Keep the token out of the logs.

Client setup

How a member points an AI client at the server.

Claude Desktop
Its config file reaches a remote server through the mcp-remote bridge. Keep header values in env: Claude Desktop on Windows mangles spaces inside args.
{
  "mcpServers": {
    "community": {
      "command": "npx",
      "args": [
        "mcp-remote",
        "http://<server>:<port>/mcp",
        "--allow-http",
        "--header", "X-Community-Token:${COMMUNITY_TOKEN}",
        "--header", "X-Member:${MEMBER}"
      ],
      "env": { "COMMUNITY_TOKEN": "<token>", "MEMBER": "member-b" }
    }
  }
}
Why --allow-http
mcp-remote refuses plain HTTP to anything but the local machine unless this flag is set. It is meant for private networks, and the tailnet is one.
Where the file lives
macOS: ~/Library/Application Support/Claude/claude_desktop_config.json. Windows: %APPDATA%\Claude\claude_desktop_config.json. Restart Claude Desktop after editing it.

Troubleshooting

What breaks first, and where to look.

The local stdio server breaks
Something wrote to stdout. In a stdio server, logs go to stderr; anything on stdout corrupts the messages.
The Member cannot connect
Check the share was accepted, the port is in the policy grant, and the URL path matches the one the server serves.
Every answer is empty
No files carry the member’s tag, or the sync has not run. Look at the manifest’s emitted_at.
Answers look old
The server answers from the last manifest it has. The Community Owner’s machine was asleep, or the sync failed.

How it works

Scan
The Community Owner’s scanner sends records for tagged files to the server
Sync
Their live vault syncs to a private copy on the server, outside the MCP zone
Ask
The Member’s AI asks what changed, sending a token and “I’m member-b”
Compare and filter
The server compares the two manifests, then narrows the result to the Member
Answer
The scoped answer returns to the Member’s AI over MCP
Baseline
The redacted manifest becomes the new baseline
Cut
The Community Owner drops a cut in their folder for the Member
Mirror
The reverse runs through the Member’s scanner and their cuts folder
Commons
Either person can add a shape to the commons; nothing else leaves

Settled

The contributor decides
Contributing a shape and granting access to the work are separate acts
Shapes, not content
The work stays on its owner’s machine or in published cuts on the server
Reading takes a second step
MCP, per relationship, through the dual-ledger gate
A token on every arrow
Every arrow into the server carries a community token
Events
Insights drop in with the name stripped; the contributor’s vault keeps the named receipt
